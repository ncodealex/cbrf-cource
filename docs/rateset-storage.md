# Получение и хранение официальных наборов курсов ЦБ

Актуальная реализация этого этапа находится в `App\Cources`. Контракты расположены в `Application/Contract`, доменные
объекты — в `Domain/Entity`. Предыдущая расширенная спецификация `exchange-rate-spec.md` описывает также будущие
механизмы и не определяет текущую схему хранения.

## Использование

Внедрите `App\Cources\Application\Service\RateSetResolver` через конструктор:

```php
$rateSet = $resolver->resolve(DatePointParser::parse('2026-10-26'));
```

`requestDate` — календарная дата: учитывается `Y-m-d` переданного DatePoint, время отбрасывается. Для текущей даты
используйте `DatePointParser::dateOf($clock->now())`: календарь переводит момент времени в `Europe/Moscow`.

Resolver сначала читает Redis, затем PostgreSQL. При отсутствии подтверждённой связи в БД Resolver немедленно пытается
захватить Redis Lock по дате запроса и повторно читает БД. Только повторный MISS приводит к запросу ЦБ. Ответ
сохраняется в БД, после успешного сохранения заполняется Redis. Все источники возвращают существующий доменный
`RateSet`.

`effectiveDate` определяется атрибутом `ValCurs.Date`, а не календарём выходных. Например, запрос на 26 октября может
вернуть набор от 24 октября. Поддерживается предварительное сохранение последнего опубликованного набора:

```php
$rateSet = $gateway->fetchLatest();
$repository->save($rateSet->effectiveDate, $rateSet);
```

`fetchLatest()` не передаёт `date_req`. Дата действия может наступить завтра.

## PostgreSQL

Единая миграция `Version20261101000000` создаёт также таблицу Import Jobs и индексы. Таблицы курсов:

| Таблица              | Столбцы                                                                                                    |
|----------------------|------------------------------------------------------------------------------------------------------------|
| `rate_sets`          | `effective_date DATE PRIMARY KEY`, `rates JSONB NOT NULL`, `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` |
| `rate_request_dates` | `requested_date DATE PRIMARY KEY`, `effective_date DATE NOT NULL REFERENCES rate_sets(effective_date) ON DELETE CASCADE`     |

Один набор хранится на одну дату действия. Несколько дат запроса ссылаются на него без дублирования котировок.
`created_at` устанавливается при первой вставке. Таблицы обслуживаются DBAL и миграцией. ORM и ORM SchemaTool не используются.

`save()` использует одну транзакцию PostgreSQL с обычным уровнем изоляции READ COMMITTED. Для каждой таблицы выполняется
INSERT с `ON CONFLICT DO NOTHING RETURNING`. При конфликте отдельный SELECT читает зафиксированную конкурентную запись.
Для набора сравнивается `contentHash()`, для календарной связи — дата действия. Идентичные записи означают успех,
различие вызывает `RateSetConflict` и откат всей операции. UPDATE, предварительного SELECT и дополнительных блокировок
нет.

`get()` ищет только точное соответствие `requested_date`. Отсутствие связи вызывает `RateSetNotFound`; ближайшая дата не
подбирается. Хэш вычисляется в памяти и отдельно не хранится.

## Представление данных и Redis

Общий `RateSetMapper` преобразует набор в структуру `effectiveDate` + список `items`. Каждый элемент содержит `code`,
`sourceId`, `nominal`, `value`, `name`, `numCode`. В JSONB сохраняется список `items`, дата берётся из столбца; в
Redis — полная структура.

`value` — строка, например `"81.4500"`. Восстановление через `BcMath\Number` сохраняет scale и завершающие нули.
Исходная стоимость номинала не заменяется стоимостью одной единицы. `numCode` также остаётся строкой, включая ведущие
нули.

Redis использует зарегистрированный сервис `Redis` и ключ `rateset:date:YYYY-MM-DD`. Значение записывается как JSON
атомарной командой SET с EX. `CACHE_DEFAULT_TTL` задаёт положительный TTL в секундах; по умолчанию в шаблоне окружения —
3600. Один набор может находиться в нескольких ключах.

Отсутствующий ключ вызывает `RateSetNotFound`. Недоступность Redis, ошибка команды или повреждённый payload вызывают
`RateSetCacheFailure`. Resolver логирует ошибку кеша и продолжает получение данных. Ошибка записи Redis не отменяет
зафиксированное сохранение PostgreSQL.

## Gateway и ошибки

`CbrRateSetGateway` использует существующий scoped HttpClient `cbr.client`: таймаут ожидания 5 секунд, максимальная
длительность 15 секунд. `CBR_BASE_URL` по умолчанию равен `https://www.cbr.ru`.

XML десериализуется Symfony Serializer в `RateSetResponse` с коллекцией `RateItemResponse`. XML-имена связаны со
свойствами через `#[SerializedName]`; дата, номинал, числовой код и значение котировки остаются строками.
`RateSetResponseDenormalizer` приводит единственный `Valute` к списку, после чего штатный ObjectNormalizer создаёт
вложенные DTO. Для определения типов коллекции PHPDoc Extractor доступен в production-зависимостях.

`CbrRateSetResponseMapper` проверяет DTO, преобразует дату, номинал и значение, затем создаёт доменные объекты. Он
отделён от общего `RateSetMapper` PostgreSQL/Redis, поскольку отвечает за внешний формат ЦБ.

XML разбирается Symfony Serializer с учётом объявленной кодировки, с LIBXML_NONET и LIBXML_NOBLANKS. Отдельной
DOM-проверки корня Gateway не выполняет. Даты, обязательные поля, номиналы и decimal strings проверяются. Дубли валют,
рубль и пустой набор отклоняются доменными конструкторами. `VunitRate` игнорируется.

- `CbrUnavailable`: transport failure, timeout и HTTP 5xx; повторяемая ошибка.
- `CbrHttpFailure`: прочие неуспешные HTTP-статусы; неповторяемая ошибка.
- `CbrRateLimited`: HTTP 429; повторяемая ошибка с Retry-After, если он корректен.
- `CbrInvalidResponse`: пустой ответ, некорректный XML или валютные данные.
- `RateSetConflict`: попытка изменить набор или подтверждённое соответствие дат.

Ошибки БД, конфликты и ошибки ЦБ передаются вызывающему коду. Автоматических повторов HTTP нет. Логи Gateway содержат
краткий контекст без полного XML.

## Проверки

Из корня репозитория:

```sh
make test
make test a="--testsuite Unit"
make test a="--testsuite Integration"
make qa
```

Тестовое окружение создаёт отдельную БД, запускает миграции и использует подмену HTTP, без реальных обращений к ЦБ.
Тесты Repository создают уникальные схемы `rateset_test_*` и удаляют только собственные схемы после проверки.
Конкурентность проверяется отдельным PHP-процессом: тест дожидается реального ожидания блокировки уникальности
PostgreSQL, затем фиксирует первую транзакцию. Redis-тесты используют отдельные ключи с TTL и очищают их.

Для ручного PHPStan сначала выполните `php bin/console cache:warmup --env=test`: анализ использует XML-контейнер
тестового окружения и обнаруживает классы миграций через `scanDirectories`.

## Следующий этап

Scheduler, RabbitMQ handlers, backfill и Import Coordinator не реализованы. Single Flight и общий RateLimiter
реализованы, но не гарантируют exactly-once при авариях Redis или истечении аренды. Сохранение остаётся идемпотентным и
атомарным. Оригинальные XML, ревизии и отдельные версии JSON не хранятся.

## Single Flight и повторы

После DB MISS используется ключ `cbr:rateset:load:YYYY-MM-DD` по requestedDate. Захват неблокирующий: занятость —
`RateSetLoadBusy`, недоступность Store и потеря владения — `RateSetLoadLockFailure`. Эти ошибки поддерживают
`Support/Retry/Application/RetryableFailure`, время повтора неизвестно. Cache/DB HIT не расходуют блокировку и лимит.

TTL задаётся параметром `app.cbr.load_lock_ttl` (30 секунд), HTTP max_duration — 15 секунд. Владение проверяется и
аренда продлевается перед Gateway, перед save и после callback. Потеря владения перед save запрещает запись. Проверки не
являются fencing: при остановке процесса непосредственно во время записи возможна потеря аренды. Уникальные ограничения
PostgreSQL остаются обязательны. Refresh по-прежнему не является общей транзакцией Redis + БД + HTTP и не
восстанавливает заранее все удалённые связи дат.

Единственный `limiter.cbr` использует Redis и token bucket: пополнение 1 токен каждые 3 секунды, burst 2. Два токена
нужны холодному `GetExchangeRate`, который последовательно загружает текущий и предыдущий наборы. При конкурентной
нагрузке оба токена могут быть уже израсходованы, поэтому успешное выполнение без повтора не гарантируется. Это
внутренний лимит приложения. Symfony RateLimiter защищает изменение состояния штатным `lock_factory`, настроенным на
Redis. Строгое хранилище состояния не превращает ошибки Redis в MISS. Все экземпляры должны использовать один REDIS_URL; Redis должен
сохранять ключи состояния и блокировок без произвольного eviction. На Redis с блокировками нельзя выполнять FLUSHDB.
Очистка кеша курсов не должна удалять ключи лимитера и Lock.

Gateway вызывает `acquire()` перед fetch/fetchLatest. Адаптер использует `consume(1)` и не резервирует будущие токены.
Исчерпание токенов — `CbrRequestRateLimitExceeded` с абсолютным retryAt; сбой Redis Lock или хранилища —
`RequestRateLimiterFailure` без известного срока. В обоих случаях HTTP не выполняется. Внутренняя блокировка может
кратко ожидать завершения конкурентного обновления состояния, но Gateway не ждёт появления токена.

Retry-After поддерживает секунды и HTTP-date, для 429 и 503. Отсутствие или некорректный заголовок дают null. retryAt —
рекомендуемая нижняя граница, а не гарантия успеха и не резервирование ресурса. RetryPolicy не выполняет sleep и не
вызывает сценарии; настройки задаёт вызывающий клиент, attempt — номер завершившегося вызова начиная с 1.

Console повторяет Handler максимум 3 раза; backoff 100/200 мс с jitter ±20%. Бюджет 300 мс начинается перед первым
вызовом и включает его длительность. Он ограничивает ожидание и начало повторов, но не прерывает выполняющийся
HTTP-запрос. Время повтора отображается с временем суток в Europe/Moscow.

Для будущего Worker: вызывать RateSetProvider, обрабатывать RetryableFailure через собственную RetryPolicy. При
разрешённом повторе сохранять Deferred и available_at, после успешного сохранения завершать текущее сообщение; при
постоянной ошибке или исчерпании попыток — Error. При ошибке сохранения состояния не подтверждать сообщение как успешно
обработанное. Занятый Load Lock и локальный отказ лимитера не увеличивают счётчик фактических внешних попыток. Worker в
этом изменении не реализован.
